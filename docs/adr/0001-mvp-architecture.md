# ADR 0001: MVP 技术架构与交付边界

- 状态：已接受
- 日期：2026-08-06

## 背景

风迹首版需要在较短周期内验证活动发布、报名和路书三个闭环，同时保证热门活动报名不超卖、轨迹在微信地图不偏移、敏感报名资料不泄露。

## 决策

- 客户端使用微信原生小程序与 TypeScript，优先保证微信地图、授权、分享和包体兼容。
- 服务端采用模块化单体。领域边界固定为活动、报名、路书、身份与通知；暂不拆微服务。
- 生产数据使用 PostgreSQL/PostGIS，Redis 用于限流、热点与短期幂等；本地自动化测试允许使用遵循同一仓储接口的内存实现。
- 报名占位、人数更新和状态变化必须在同一事务内，使用唯一约束与幂等键形成多层保护。
- 原始轨迹保存 WGS84，微信地图展示前转换为 GCJ-02，并按缩放等级返回抽稀轨迹。
- 第一版产品文案使用“路书展示/轨迹跟随”，不承诺专业逐向导航。

## 后果

- 模块化单体降低首版部署和排障成本，但模块之间只能通过公开服务接口交互。
- 内存仓储便于测试和本地演示，但生产接入 PostgreSQL 仓储前不得对外上线。
- 微信登录、订阅消息、内容安全、腾讯地图和 COS 都需要在获得正式环境配置后完成真机验收。

## MVP 阻断项

- 报名并发测试不能证明零超卖。
- 敏感字段以明文写入日志或数据库。
- 活动关键字段变更未通知已报名用户。
- 坐标转换和真实路线真机抽查未完成。
- 隐私协议、活动免责声明和数据保留策略未完成合规审核。
