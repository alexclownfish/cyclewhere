# 公路骑行小程序 MVP：质量保障与 Agent 协作流程

## 1. 质量目标与范围

MVP 的三条核心用户链路是：

1. 发起者创建、编辑、发布和取消活动；
2. 骑友查看活动、报名、取消报名，发起者管理名单；
3. 骑友查看路书、海拔与关键点，并从活动页使用对应路书。

首版质量目标：

- 核心链路无 P0/P1 缺陷；核心端到端用例通过率 100%；
- 报名名额在并发场景下不超卖、不重复报名；
- 涉及支付时，支付状态以后端异步通知为准，订单处理幂等；
- 定位、手机号、头像昵称等信息遵守最小必要、明确告知和可撤回原则；
- 路书坐标、距离和海拔展示一致，错误坐标系不会导致线路偏移；
- 线上错误、性能和业务指标可观测，具备回滚和降级路径。

建议首版暂不承诺实时语音导航、复杂轨迹编辑、俱乐部财务结算、保险自动核保。它们会显著扩大合规、地图精度和资金风险。若收费报名不是首发刚需，可先以免费活动验证核心闭环。

## 2. 测试金字塔

### 2.1 单元测试（约 65%）

覆盖纯业务规则和边界，执行要快，可在每次提交运行：

- 活动状态机：草稿、已发布、已满员、已结束、已取消；
- 报名资格、重复报名、容量计算、候补递补、截止时间；
- 金额计算、退款比例、订单状态机与幂等键；
- 距离、配速、爬升、时间和单位格式化；
- GPX/路书解析、异常点过滤、坐标转换、路线简化；
- 权限校验：普通用户、活动发起者、运营管理员；
- 输入校验：标题、时间、人数、费用、联系方式、图片和文本长度；
- 敏感字段脱敏与日志过滤。

覆盖率建议：核心领域模块语句/分支均不低于 85%，全项目语句不低于 75%。覆盖率不是放行的唯一标准，报名与支付状态机必须用状态迁移用例完整覆盖。

### 2.2 服务/集成测试（约 25%）

使用独立测试数据库和沙箱能力，验证真实边界：

- 数据库唯一约束与事务：同一用户同一活动只能有一条有效报名；
- 20～100 个并发报名请求争抢最后名额，不超卖；
- 微信登录会话换取、过期和失败重试；
- 支付下单、签名验证、重复回调、乱序回调、退款回调；
- 对象存储上传、文件类型/大小限制、失效资源；
- 地图服务超时、限流、空结果和错误坐标；
- 定时任务：报名截止、活动结束、未支付订单关闭；
- 数据迁移向前兼容与回滚演练。

所有外部服务同时具备契约测试和可控 mock。正常路径可用沙箱验证，错误路径通过 mock 稳定复现。

### 2.3 端到端测试（约 10%）

只保留高价值主路径，避免脆弱且昂贵的全量 UI 自动化：

- 新用户授权必要信息后浏览活动；
- 发起者建立含路书的活动并发布；
- 骑友报名，活动页和名单人数同步；
- 骑友取消报名，名额恢复，候补用户正确递补；
- 满员、截止、取消、下架等状态下按钮与服务端行为一致；
- 路书地图、关键点、距离和海拔加载成功，弱网有明确状态；
- 若启用支付：下单、支付成功回调、取消/超时、退款完整闭环。

小程序自动化测试之外，发布前必须在至少一台 iOS 与一台 Android 真机完成冒烟；开发者工具通过不能替代真机定位、支付、后台切换和弱网验证。

### 2.4 非功能测试

- 性能：首页与活动详情首屏、地图包体与点位数量、图片压缩、API P95；
- 稳定性：弱网、断网、重复点击、后台恢复、服务超时和重试风暴；
- 兼容性：近两年主流 iOS/Android、微信基础库最低支持版本；
- 可用性：空、错、加载、无权限、已取消等状态完整；
- 无障碍：可读字号、颜色对比、按钮可点击区域、图片替代描述；
- 安全性：依赖扫描、密钥扫描、权限越权、注入、上传文件、接口限流。

## 3. 关键验收用例

| ID | 场景 | 验收标准 | 等级 |
|---|---|---|---|
| A-01 | 创建并发布活动 | 必填项、时间顺序、人数上限校验正确；发布后生成可访问详情 | P0 |
| A-02 | 修改/取消活动 | 仅发起者可操作；重大变更有提示；取消后禁止新报名并通知已报名用户 | P0 |
| S-01 | 正常报名 | 服务端校验资格并创建唯一记录；人数、名单、用户状态一致 | P0 |
| S-02 | 重复点击/重试 | 相同请求只产生一次报名或订单，返回结果稳定 | P0 |
| S-03 | 最后名额并发争抢 | 成功人数不超过剩余名额，失败方得到明确原因 | P0 |
| S-04 | 截止/满员/取消后报名 | 前端不可提交，绕过前端请求也被服务端拒绝 | P0 |
| S-05 | 取消与候补递补 | 名额原子释放；候补按明确规则递补且有通知 | P1 |
| R-01 | 路书加载 | 线路、起终点、关键点、距离、爬升一致且视野自动适配 | P0 |
| R-02 | GPX 异常数据 | 空文件、超大文件、坏点、无海拔有可理解的错误或降级 | P1 |
| R-03 | 坐标正确性 | WGS84/GCJ-02 边界明确；抽样地标无明显线路漂移 | P0 |
| R-04 | 弱网与地图失败 | 页面不白屏；支持重试；活动文字信息仍可查看 | P1 |
| P-01 | 支付成功 | 仅后端验签后的异步通知改变支付状态；金额与订单匹配 | P0 |
| P-02 | 回调幂等与乱序 | 重复、延迟、乱序通知不重复记账、不回退最终状态 | P0 |
| P-03 | 退款 | 权限、金额、状态正确；失败可重试且留审计记录 | P0 |
| C-01 | 隐私同意与撤回 | 使用前告知目的；非必要权限拒绝后核心浏览可用；支持注销/删除请求 | P0 |
| C-02 | 越权访问 | 用户不能读写他人隐私资料、报名或订单；发起者权限限定在自己的活动 | P0 |

每个验收用例必须附自动化结果或真机证据（录屏/截图、测试环境、版本号和时间），不能只写“已自测”。

## 4. 高风险能力控制

### 4.1 安全

- 客户端不保存服务端密钥、支付私钥、地图服务端 Key；密钥由环境变量/密钥管理系统注入；
- 所有鉴权与活动权限在服务端复核，不能相信客户端传入的用户 ID、价格和角色；
- 报名接口使用数据库事务、唯一索引和条件更新实现容量约束；仅靠“先查询再写入”会超卖；
- 写操作支持幂等键、防重复提交、频率限制与审计日志；
- 富文本、昵称、路书名称和上传文件做白名单校验，防注入、恶意脚本和伪造文件；
- 日志禁止出现 `code`、session key、手机号明文、支付凭证、精确实时位置；
- 管理后台强认证、最小权限，敏感操作保留操作者、时间和变更前后值；
- 上线前执行 SAST、依赖漏洞、Secret 扫描和基础接口越权测试。

### 4.2 隐私与合规

- 建立数据清单：字段、用途、法律/授权依据、存储位置、保留期限、共享对象和删除方式；
- 遵循《个人信息保护法》等适用规则及微信小程序平台最新隐私规范；隐私政策、平台隐私保护指引和实际代码保持一致；
- 精确位置属于高风险信息：仅在用户主动查看当前位置或导航时调用，说明用途，按需单独取得同意；不要持续后台采集；
- 报名默认不公开手机号、身份证、紧急联系人等信息。发起者只看到履约必需内容；
- 第三方地图、统计、客服、支付 SDK 形成清单，披露其主体、用途与数据类型，删除未使用 SDK 权限；
- 提供权限拒绝后的降级体验，以及个人信息查询、更正、删除、撤回授权和账号注销路径；
- 制定数据保留期限，活动结束后对非必要精确位置、联系方式进行删除或匿名化；
- 未成年人参与、骑行免责说明、健康风险提示不应被“免责条款”替代安全保障义务，法务文本需正式复核。

### 4.3 支付与退款

- 支付能力以微信支付当前商户资质、类目和平台规则为准；明确平台是信息服务还是活动收费主体；
- 订单金额由服务端按活动配置计算，客户端金额仅用于展示；下单前冻结或保留名额要有超时释放机制；
- 支付结果以后端验签的异步通知为准，不以客户端“支付成功”页面为准；
- 回调验签、订单号/商户号/金额匹配、幂等处理、状态机单向推进；
- 退款规则在报名之前清晰展示；部分退款、重复退款、退款失败和活动取消批量退款均需测试；
- 每日进行订单、支付平台流水、报名记录三方对账，异常进入人工处理队列；
- 客服能查询审计轨迹，但无权修改原始支付流水。

### 4.4 地图、路书与户外安全

- 明确存储坐标系与展示坐标系。GPX 常为 WGS84，国内地图通常使用 GCJ-02；转换只发生一次并有地标回归样本；
- 路线简化保留起终点、急弯、补给点、危险点，按缩放级别控制点数，避免地图渲染卡顿；
- 距离与爬升算法固定版本并记录；海拔噪声需平滑，原始数据缺失时明确标识；
- 地图 Key 按小程序 AppID、域名/IP 等能力限制，设置配额与费用告警；
- 第三方路线与地图数据遵守许可和署名要求，不将抓取数据直接商用；
- 明确提示路书仅供参考，路线可能受施工、封路、天气影响；危险点和紧急联系人应易于访问；
- 地图服务失败时保留活动时间、集合点文字、联系人等必要信息，避免整个详情页不可用。

## 5. CI 门禁

建议采用保护分支和 Pull Request 流程，禁止直接推送主分支。每个 PR 必须通过：

1. 格式化、Lint、类型检查；
2. 单元测试与覆盖率阈值，核心业务文件不得降低覆盖率；
3. 服务/契约测试，数据库迁移在临时库执行；
4. 构建小程序及后端产物，校验包体积和环境变量；
5. SAST、依赖漏洞、许可证与 Secret 扫描；
6. 核心 E2E 冒烟（合并前或受控测试环境）；
7. 至少一名非作者 Reviewer 批准；报名、支付、权限、隐私变更须增加领域 Reviewer；
8. PR 模板填写需求链接、风险、测试证据、数据/接口变更、回滚方案。

门禁原则：

- 任一 P0/P1 缺陷、失败测试、高危漏洞、密钥泄露直接阻断；
- 不允许用跳过测试、降低阈值或宽泛忽略规则来通过 CI；例外需技术负责人注明范围、期限和补救任务；
- 测试不稳定要当作缺陷管理；先隔离并指定负责人和修复期限，不让随机重跑掩盖问题；
- 产物由 CI 一次构建后逐环境晋级，不在生产重新手工构建；
- 数据库迁移需向前兼容，先扩展后收缩，发布过程中支持新旧版本短暂共存。

建议核心指标：提交到可反馈时间少于 10 分钟；主分支始终可发布；失败门禁有明确责任 Agent；CI 证据保留至少一个发布周期。

## 6. 发布检查表

### 发布前

- [ ] 需求与非目标冻结，核心验收用例全部通过；
- [ ] 无未处理 P0/P1，P2 有负责人、期限和用户影响说明；
- [ ] iOS/Android 真机冒烟完成，弱网、拒绝权限、后台恢复已验证；
- [ ] 隐私政策、平台隐私指引、权限声明、SDK 清单与代码一致；
- [ ] 小程序类目、内容规范、地图许可、支付资质和法务文本已确认；
- [ ] 生产密钥独立配置并轮换，测试账号/测试支付配置未混入生产；
- [ ] 数据库迁移、备份恢复、回滚脚本在预发布环境演练；
- [ ] 监控面板和告警生效：登录成功率、发布成功率、报名成功率、超卖、支付差错、接口 P95/错误率、地图失败率；
- [ ] 客服 FAQ、活动取消/退款/投诉流程和紧急联系人就绪；
- [ ] 发布负责人、观察窗口、回滚判据与回滚决策人明确。

### 发布中

- [ ] 记录前后端版本、配置与数据库迁移版本；
- [ ] 先灰度到内部/小流量，执行核心冒烟后再扩大；
- [ ] 观察错误率、业务成功率、支付回调积压和数据库资源；
- [ ] 不在观察期同时发布无关高风险变更。

### 发布后

- [ ] 对照发布基线持续观察至少 30～60 分钟；
- [ ] 抽查真实活动发布、报名、取消、路书和支付对账；
- [ ] 出现超卖、错账、越权、隐私泄露立即停止相关入口并启动事件响应；
- [ ] 24 小时内回顾告警和客服反馈，必要时形成修复版本；
- [ ] 事故完成无责复盘，补充自动化用例和防复发门禁。

## 7. Agent 分工与互相督促

### 7.1 建议角色

| Agent | 主责 | 强制复核对象 | 交付物 |
|---|---|---|---|
| 产品/验收 Agent | 用户故事、边界、验收标准、非目标 | 架构与 UI 是否覆盖流程 | PRD、状态表、验收清单 |
| 架构/后端 Agent | 领域模型、API、事务、权限、支付 | 前端契约与测试设计 | ADR、OpenAPI、迁移、服务测试 |
| 小程序/UI Agent | 页面、状态反馈、授权降级、性能 | 产品验收与接口契约 | UI、组件、前端测试、真机证据 |
| 路书/地图 Agent | GPX、坐标、距离爬升、地图降级 | 后端数据模型与真机表现 | 算法说明、样本、地图回归测试 |
| QA/安全 Agent | 测试策略、风险测试、CI、发布 | 所有高风险变更 | 测试报告、漏洞报告、放行意见 |

小团队可以一人承担多个角色，但同一变更的实现者和最终批准者不能是同一个 Agent。支付、权限、个人信息、坐标转换至少需要双人/双 Agent 复核。

### 7.2 工作流

1. **领取任务**：产品/验收 Agent 先提供验收标准、失败场景和非目标；实现 Agent 回复理解与风险。
2. **先定契约**：跨端变更先提交数据模型、接口契约或 ADR；相关 Agent 对字段、状态码、幂等和兼容性确认。
3. **实现与自测**：实现 Agent 同步代码、测试、迁移、埋点和文档，提供可复现命令及证据。
4. **交叉审查**：领域 Agent 查业务正确性，QA/安全 Agent 查负向场景和门禁；Reviewer 必须指出已检查范围，禁止只有“LGTM”。
5. **对抗验证**：Reviewer 主动尝试重复请求、越权、并发、弱网、坐标错误、乱序回调等失败路径。
6. **修复闭环**：每条意见标为“接受并修复 / 有证据拒绝 / 另建任务”；高风险意见未关闭不能合并。
7. **集成验收**：产品 Agent 按验收用例验收，QA Agent 核对 CI 与真机证据并出具放行结论。
8. **发布观察**：发布 Agent 负责执行检查表；其他 Agent 在观察窗口各自盯业务、技术和安全指标。

### 7.3 Agent 沟通模板

任务交接必须包含：

```text
目标 / 非目标：
影响文件与接口：
业务与技术风险：
验收用例：
已运行的测试及结果：
未覆盖项与原因：
上线与回滚方式：
需要哪位 Agent 复核什么：
```

审查结论必须包含：

```text
结论：通过 / 修改后通过 / 阻断
检查范围：
发现及严重级别：
复现证据：
要求补充的测试：
残余风险与负责人：
```

### 7.4 冲突与升级

- 争议优先由验收标准、复现测试、日志和平台官方规则裁决，不按角色资历拍板；
- P0/P1、安全、隐私、支付或数据丢失风险有一票阻断权，由技术负责人和对应领域负责人共同解除；
- 如果规则确需例外，记录 ADR：背景、备选方案、决定、风险、责任人、失效日期；
- Agent 发现不属于自己模块但会阻断上线的问题，必须创建问题并通知责任 Agent，不得静默绕过；
- 每个里程碑由 QA Agent 做一次需求-代码-测试可追溯检查，防止功能完成但验收证据缺失。

## 8. 完成定义（Definition of Done）

一个需求只有同时满足以下条件才算完成：

- 验收标准和失败场景均已验证；
- 代码、接口、数据迁移、日志/指标和必要文档同步完成；
- 单元、集成和适用的 E2E/真机测试通过；
